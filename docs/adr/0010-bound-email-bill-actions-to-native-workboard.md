# Bound email bill actions use native Workboard

Status: accepted for implementation; installed qualification and activation remain gated.

Deciding issues: [#331](https://github.com/AshleyHollis/openclaw-command-center/issues/331), [#340](https://github.com/AshleyHollis/openclaw-command-center/issues/340), [#341](https://github.com/AshleyHollis/openclaw-command-center/issues/341), [#342](https://github.com/AshleyHollis/openclaw-command-center/issues/342).

## Decision

The first family is an already admitted, explicit email payment obligation with an applied intake-accounting outcome and an exact authorized retained Note. Existing accepted extraction and commitment capture supply its identity and evidence. Admission reserves a scoped native manual Workboard todo card using an immutable create intent. Native card status and supported native events remain canonical. Handled means observed native Done; it makes no payment claim.

The existing SQLite operation journal owns namespaced bill binding, immutable operation receipts and revisioned notification eligibility. No database schema, separate work lifecycle, provider integration or timing worker is added. Generic journal writes cannot replace these reserved owner records. Uncertain writes remain unknown, keep their original operation ID and revision, and suppress competing choices until the original operation is reconciled or retried unchanged.

Exact correlation reuses a binding only for the same literal admitted loop and unchanged accepted financial/deadline meaning. A routine source version may refresh evidence without reopening Done. Ambiguous aliases, changed meaning and missing evidence require review. Topic moves preserve identity when the existing literal loop and current exact source remain authorized.

Explicit email payment obligations may carry a closed versioned `paymentIdentity` in the existing accepted plan and observation JSON. Amount is a nonnegative safe integer in minor units paired with an explicit uppercase three-letter currency; invoice, account, payee and purpose identifiers are accepted exact strings. The owner never extracts these facts from titles, coerces values, or supplies a currency scale. Missing legacy facts remain missing. Adding or changing accepted financial/deadline meaning on an existing binding produces conflict and cannot reopen Done or reset Later.

A separately accepted new cause uses a distinct existing namespaced correlation and may name an exact predecessor loop, accepted observation and explanation. Initial admission resolves that durable applied email outcome, independently checks its original retained Note and current Topic authority, and rechecks those rights at final native admission. The relation does not replace, reopen or settle the prior action. Ordinary reads and actions on the new request remain usable after predecessor access loss; the unavailable predecessor projection is omitted. Review of the predecessor reads the named original observation, never a later observation or a cached link.

Later retains a UTC instant, explicit IANA zone, disclosed offset and eligibility revision. It changes notification eligibility only. Attention open/refresh evaluates eligibility using server time. Native Done takes precedence; there is no push, polling, Discord or autonomous resurfacing worker.

## Alternatives and consequences

A custom action database/lifecycle was rejected because native Workboard and the existing journal already own the required state. Inferring payment completion from Done or copied email text was rejected because neither establishes payment.

The projection reports only currently authorized bound actions with honest partial coverage. It cannot claim all mail was scanned or all unpaid obligations admitted. Current accepted reader locators identify destinations; they do not attest live provider permissions. Review uses the exact permitted retained Note or independently permitted current Outlook locator, never a cached evidence copy.

Automatic admission remains excluded: explicit admission must name and verify its native tenant/board. The native prerequisite reserves the original scoped create identity and canonical create intent within the existing SQLite card owner transaction. Its scoped schema migration and cross-process tests belong to OpenClaw; this decision adds no CC table or parallel lifecycle owner. Native explicit hard deletion retains its existing lifecycle and removes the card reservation.

Authenticated host authority and the adapter's source fence must reach actual native SQLite mutation admission. Source tests, fictional browser tests and journal restart tests are distinct from exact installed host/package qualification. The production release flag stays false until that qualification, supported Linux process-death evidence and the eventual qualified predecessor are accepted. Existing deployment pins and runtime state are unchanged.
