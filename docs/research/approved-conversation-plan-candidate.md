# Track an approved Conversation plan — bounded candidate

Owner: [#370](https://github.com/AshleyHollis/openclaw-command-center/issues/370), within #248 and the manual-request design in #313/#331. Delivery class: **3** (journal correlation and external card creation). This is an unregistered source candidate, not a complete or release-qualified feature.

## Concrete fictional journey

In the fictional Garden Topic Conversation, review “Prepare a reviewed planting plan”: draft the planting plan, compare a fictional budget, present both for review. The review shows the exact originating Conversation message, outcome, ordered steps, completion criteria and explicit tenant/board destination. Choose **Track this plan** to retain that exact acceptance and create one native todo card. Read back the card identity, scope and native revision. Native Start remains a separate explicit action. Check tracking status after uncertainty; an explicit retry preserves the frozen acceptance. An edited plan cannot reuse its acceptance identity.

The candidate component accepts an already concrete reviewed input. It does not extract a plan from arbitrary prose, manufacture a source message identifier, choose a default destination or register a native Chat action. The rendered fixture connects this component to the real CC SQLite owner through a fictional HTTP harness. Workboard and source transports in these fixtures are simulated; this is not authenticated native-owner qualification.

## Ownership and representation

`approved-conversation-plan.v1` is separate from the closed email/payment family. `operation_journal` stores the original acceptance, source/membership revision, operator, native destination, scoped create intent and exact card correlation. The immutable acceptance includes the original logical operation ID; another click can have its own immutable operation receipt while resolving the same binding. No table or migration, queue, scheduler, execution lifecycle, notification worker or progress database is added. Generic journal writes cannot replace the reserved family.

The native payload uses supported title, notes, todo, tenant, board and idempotency key. Native title/notes/scope limits are checked before acceptance; no truncation occurs. It deliberately omits an execution object: on the pinned native owner a mode-only object normalizes away, while fabricating execution identifiers would create a misleading execution record. Native todo admission does not Start, specify, decompose or schedule. Native owns subsequent card edits and lifecycle. The accepted CC snapshot remains immutable even after native edits.

Read/reconciliation uses `workboard.cards.list`, not an invented cards.get. Exact card ID, tenant, board, idempotency key and finite updatedAt are checked. Unbound response-loss recovery also verifies the original native title/notes. No attributable native execution receipt is fabricated. Missing cards remain unknown and are not recreated automatically. Explicit unchanged Track retry uses the original idempotency key. Linked attempt projection requires nonempty exact card sessionKey/runId and a matching native attempt; unlinked historical attempts never count as current progress. Done, blocked and review are native status observations only.

## Verified source facts and blockers

Inspected source pair: CC `2253d49b5b90c8c1c8c506a0a38efe300c389da4`, Life `26a9c0faa4124e53ae2eab34291d68a7245f630c`. GitHub main was separately inspected at `291083e4ea381a4edecd56f3fadf9f5b590a3aee`; it is not this feature's baseline. Frozen filing and everyday-workspace branches are untouched.

1. **Exact source-message admission:** existing CC Sessions history verifies native Session key/id around transcript retrieval (`src/sources/sessions.mjs`), but it does not expose a qualified immutable message acceptance with a synchronous current message/membership fence at native admission. The candidate requires `readSource` and `assertSourceCurrent`; no production implementation is claimed. The real owner must bind actual message evidence without trusting caller-supplied identity/digest and recheck reset, Topic reassignment and revoked access. Life #340 supplies create/update commit guards, not a new source-message owner.
2. **Open the exact native card:** pinned native `ui/src/plugins/control-ui-host.ts` resolves page navigation against the owning plugin's descriptors. `ui/src/pages/workboard/route-location.ts` resolves a board route; it does not specify an exact card target. The component exposes an injected exact-card navigation seam for the fictional fixture only. Resolve a supported native card navigation contract before wiring Topic/Chat. A hand-built route or DOM click is not a substitute.
3. **Explicit human request:** native card status, worker protocol, diagnostics and notifications do not provide the closed, revisioned human-question/approval/requested-result-review envelope needed here. The candidate publishes no eligible Attention. A generic blocked/review state or completion cannot manufacture a human request. Qualify a native request owner and its resolution/revision semantics before implementing Attention, deduplication or response controls.
4. **Production composition and qualification:** authenticated bridge methods, concrete source adapter and Topic/dashboard/Chat registration are intentionally absent. The candidate factory fails when any required owner is missing. Real authenticated Workboard/SQLite cross-process create/readback qualification, final-head CI, compiled exact-pair and installed browser tests remain required. Progress-card/session-summary consumption must also verify exact linked-session/run identity; replaceable display cannot become a queue.
