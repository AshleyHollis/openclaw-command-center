# Reusing existing packages for Topic Notes

Research date: 2026-09-13. Public documentation, source, GitHub release metadata and npm registry metadata only; no packages installed and no live state inspected. This is an implementation recommendation, not a new architectural decision or release qualification.

## Recommendation

No investigated OpenClaw plugin is a drop-in replacement for read-only browsing of an existing Topic's authoritative Note Folder inside native Control UI. The lowest-effort compatible fallback is a stock Web Awesome tree plus `markdown-it` and DOMPurify, connected to Command Center's existing authorized Notes reads. Keep Topic ownership, Source Recovery and path containment in the existing backend. Let the stock component own tree keyboard navigation, selection and expansion; do not build another keyboard/state framework.

Native Files is worth reusing if a supported Topic-compatible contract becomes available, but browsing a session workspace does not establish Topic ownership. `memory-wiki` would change the knowledge workflow: it maintains compiled wiki content. Standalone dashboards would replace the required native surface. These conclusions follow the comparison below and the repository's [first-release decision](../adr/0004-first-live-release-core-topics-notes-chat.md) and [domain definitions](../../CONTEXT.md).

### Memory wiki: real native functionality, different source ownership

The [official guide](https://docs.openclaw.ai/plugins/memory-wiki) describes a compiler for durable knowledge, with isolated, bridge and unsafe-local input modes. Bridge mode consumes public memory artifacts. Obsidian rendering produces wiki pages; it is not a contract to display an existing Note Folder unchanged. Replacing Topic Notes with it would require a separate product decision about imported/generated content and ownership.

The [released Gateway implementation](https://github.com/openclaw/openclaw/blob/v2026.9.4/extensions/memory-wiki/src/gateway.ts) registers reads under `operator.read`, writes such as `wiki.apply` under `operator.write`, and local-file ingestion under `operator.admin`. Its comment explicitly describes the overview consumer as version-locked Control UI. Public visibility of source and Gateway methods does not establish a supported reusable UI component or cross-plugin client. The package is private, so do not import its internals into Command Center.

### File browsers: usable elsewhere, no native replacement

The Telegram plugin's [entry point](https://github.com/timotme/openclaw-telegram-chat-file-browser/blob/df85d92287d750065de688f3ae6196fd38e210f3/index.ts) registers `requireAuth: true` commands; its [file reader](https://github.com/timotme/openclaw-telegram-chat-file-browser/blob/df85d92287d750065de688f3ae6196fd38e210f3/src/file.ts) reads an entire text file and then slices the preview. It provides no Topic identity or native operator-authority integration. A preview length setting is not a bounded file read.

ClawUI's [file component](https://github.com/ketthub/clawUI/blob/18c5b2264fff895a4909b78b34023d11b4f8906e/src/components/FileManager.tsx) depends on its renderer and file API. Its [Vite middleware](https://github.com/ketthub/clawUI/blob/18c5b2264fff895a4909b78b34023d11b4f8906e/vite-fs-plugin.ts) checks configured roots and realpaths but also implements upload, write and delete, and sets wildcard development CORS. Those are separate host filesystem operations, not native Gateway operator scopes. This is evidence of architectural mismatch, not a comprehensive security audit.

The other dashboard's [viewer](https://github.com/oealgo/openclaw-dashboard/blob/768259e66a07d1cffb5575d8e9a1cfd4737ecbda/frontend/src/components/common/FileViewer.tsx) imports `react-markdown` and app-specific utilities. Its separate backend and frontend build are visible in the package scripts. Neither alternative minimizes work for the current HTMLElement-based plugin surface.

### Native Files baseline

The [released native Chat documentation](https://github.com/openclaw/openclaw/blob/v2026.9.4/docs/web/control-ui/chat.md) describes Files and Review, with session/project/artifact browsing, `sessions.files.get`, a 256 KiB UTF-8 limit, and containment plus symlink/hardlink guards. Eligible administrator connections can edit through `sessions.files.set`. The text view is documented as a code view in that release. Native session roots, editing authority and Topic-owned read-only Notes are different contracts; do not infer equivalence or change bindings merely to reuse the UI. Newer main-branch Markdown attachment improvements also do not prove a released Note Folder reader.

## Concrete package fallback

Use the free core `@awesome.me/webawesome` package's `<wa-tree>` / `<wa-tree-item>`, with one file-selection listener calling the existing read operation and a formatted article beside it. Import the component entry directly (`@awesome.me/webawesome/dist/components/tree/tree.js`); use normal DOM elements and events, without React adapters. [Tree docs](https://webawesome.com/docs/components/tree/) expose selection, expansion and lazy-load events. The [3.12.0 source](https://github.com/shoelace-style/webawesome/blob/v3.12.0/packages/webawesome/src/components/tree/tree.ts) implements arrows, Home/End, Enter/Space and focus movement. It is Lit-based internally; consumers need no Lit application migration.

As checked, [npm publishes 3.12.0](https://registry.npmjs.org/@awesome.me%2Fwebawesome), dated 2026-08-21, under [MIT](https://github.com/shoelace-style/webawesome/blob/v3.12.0/LICENSE.md). Component imports include tree-item and subordinate checkbox/icon/spinner code. The package also contains React and SSR adapters, but the direct tree entry does not import the React adapter. Bundle the selected components and required assets locally, measure actual output size, and avoid a runtime CDN dependency. [Browser policy](https://github.com/shoelace-style/webawesome/blob/v3.12.0/packages/webawesome/docs/docs/resources/browser-support.md) targets the latest two major browser versions; verify the actual embedded/browser host and theme integration before adoption.

Pair it with browser-bundled `markdown-it` (MIT) and DOMPurify (choose its Apache-2.0 licensing option and retain required notices). Current registry versions are [markdown-it 15.0.2](https://registry.npmjs.org/markdown-it), published 2026-09-11, and [DOMPurify 3.4.15](https://registry.npmjs.org/dompurify), published 2026-09-06. These are availability observations, not an instruction to upgrade existing dependencies blindly. Both expose browser/ES-module distributions; DOMPurify needs the browser DOM and no runtime npm dependencies. See [markdown-it license](https://github.com/markdown-it/markdown-it/blob/master/LICENSE) and [DOMPurify license](https://github.com/cure53/DOMPurify/blob/main/LICENSE).

Proposed rendering policy: disable raw HTML in Markdown, sanitize the final rendered HTML, block automatic remote images, and resolve local Note links only through the existing verified Topic source boundary. Rendering packages do not enforce filesystem ownership, stale-response handling, note size limits or Source Recovery. The component replaces tree mechanics; a small adapter still maps verified Note identifiers to rows and handles loading, errors and selection changes. Basic Markdown is the first target; Obsidian embeds, wikilinks and other extensions require separate deliberate support.

This recommendation needs a bounded implementation and browser check, not a new framework: one existing Topic fixture with nested Notes, keyboard selection, formatted headings/lists/tables/code, rejected unsafe links, missing-folder recovery and stale-selection response handling. No claim is made that this unimplemented combination has passed those checks.
